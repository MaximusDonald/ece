ECO-Compliance Engine — App Map & Learning Guide

Plateforme B2B souveraine d'audit documentaire automatisé pour la CEDEAO/UEMOA — Guide de réutilisation des patterns clés

🏗️ Architecture Globale

Backend (FastAPI)

  • app/main.py — App factory, lifespan, routers
  • app/core/ — config, database, security
  • app/models/ — SQLModel (User, Project, Document, LegalSource, RiskFinding, ReportVersion...)
  • app/api/ — auth, projects, documents, reports, jobs, admin
  • app/workers/ — Celery tasks (extraction, semantic, legal_research, scoring, report, incremental)
  • app/services/ — minio, llm, pdf, diff
  • app/seed/ — corpus juridique initial (~30 textes)

Frontend (Next.js 15)

  • src/app/(auth)/ — login, register
  • src/app/dashboard/ — projects, upload, analysis, reports, admin
  • src/components/ui/ — shadcn-ui components (Button, Card, Table, Tabs, etc.)
  • src/hooks/useApi.ts — TanStack Query hooks typés
  • src/lib/api.ts — client Axios + types partagés

Infrastructure (Docker Compose)

  • PostgreSQL 16 + PGVector (port 5432)
  • Redis 7 (port 6379) — broker Celery + cache
  • MinIO (ports 9000/9001) — stockage S3-compatible
  • Backend FastAPI (port 8000)
  • Frontend Next.js (port 3000)
  • Celery Worker (concurrency=2)

🔄 Parcours Utilisateur (Core Journey)

1
Auth & Projet — Inscription → création projet (pays BJ, secteur, traitements)
2

6
Admin Gouvernance — Corpus, règles scoring, modèles LLM, pays, audit logs

🧠 Noyau Distinctif (Unique Kernel) — Patterns Réutilisables

🎯

RAG Souverain avec Consensus & Badges de Confiance

Fichiers clés : backend/app/workers/legal_research.py (run_consensus, hybrid_search), backend/app/services/llm_client.py

  • Sources curatorées uniquement — Pas de web ouvert, corpus interne vérifié avec hash SHA-256, URL officielle, autorité, date
  • Recherche hybride PGVector — Similarité cosinus + filtrage SQL (pays, niveau, statut) → top-k chunks
  • Consensus LLM structuré — Prompt avec sortie JSON forcée : risque (5 niveaux), confiance (High/Medium/Low), sources matchées, flags obsolescence/conflit, recommandation
  • Badges de confiance explicites : High (≥2 sources concordantes), Medium (1 source ou info partielle), Low (zone floue, info manquante)
  • Détection d'obsolescence — Textes abrogés marqués [Abrogé/Ancien] via champ abrogated_date
  • Détection conflits de normes — CEDEAO vs national affiché côte à côte au lieu de choisir silencieusement
💡 Pattern réutilisable : Pour tout système d'analyse documentaire réglementaire : (1) corpus versionné avec métadonnées riches, (2) recherche vectorielle filtrée par juridiction/domaine, (3) prompt LLM avec sortie JSON typée incluant niveau de confiance, (3) post-traitement déterministe pour badges et flags.
⚖️

Scoring Déterministe + Ajustement par Confiance

Fichier clé : backend/app/workers/scoring.py (run_scoring)

  • 5 niveaux de risque : Conforme (0) → À surveiller (5) → Modéré (10) → Élevé (15) → Critique (25)
  • Règles configurables par domaine/pays — Pondérations + seuils de confiance en base (ScoringRule)
  • Ajustement par confiance : Findings Low à risque Élevé/Critique rétrogradés automatiquement
  • Confiance globale : High si >60% findings High, Medium si >30%, sinon Low
💡 Pattern réutilisable : Séparer le scoring LLM (probabiliste) du scoring métier (déterministe). Stocker les règles en base pour les faire évoluer sans redéployer. Utiliser la confiance comme modificateur de sévérité, pas comme score direct.
🔄

Mise à Jour Incrémentale + Diff de Versions

Fichiers clés : backend/app/workers/incremental.py, backend/app/services/diff_engine.py

  • Identification ciblée — Le contexte complémentaire (ex: localisation hébergement) ne ré-analyse que les findings concernés
  • Chaînage de versions — ReportVersion.parent_version_id crée un historique linéaire
  • Diff ligne par ligne — difflib.SequenceMatcher → marqueurs [Nouveau], [Résolu], [Mis à jour]
  • UI de comparaison — Vue côte à côte avec surlignage des changements
💡 Pattern réutilisable : Pour tout système de révision documentaire : (1) lier les zones floues à des champs précis, (2) n'exécuter que le sous-graphe du pipeline impacté, (3) versionner les sorties avec parent_id, (4) diff algorithmique standard pour l'affichage.
🛡️

Client LLM Unifié + Mock pour Développement

Fichier clé : backend/app/services/llm_client.py

  • Interface unique — LLMClient avec chat_completion() + get_embeddings()
  • Multi-fournisseurs — OpenAI (gpt-4o-mini) + Anthropic (claude-3-5-haiku), sélection par clé API dispo
  • Format JSON forcé — Paramètre response_format="json" pour sortie structurée fiable
  • Mock client — MockLLMClient pour développement sans clés API (réponses déterministes)
💡 Pattern réutilisable : Toujours abstraire le client LLM derrière une interface. Le mock permet : tests unitaires déterministes, développement offline, CI sans coûts API, démonstrations démo-ready.

🗃️ Modèle de Données Clé (SQLModel)

Utilisateur & Organisation

  • User — email, role (org_admin, analyst, reader, external_auditor, platform_admin), org_id
  • Organization — name, plan, users[]
  • Project — org_id, name, country_code (ISO), sector, treatments[], status

Document & Extraction

  • Document — project_id, filename, mime_type, minio_bucket/object, status
  • DocumentExtraction — markdown, quality_score (0-1), page_count, language
  • DocumentAnalysis — entities{}, vague_zones[]

Corpus Juridique & Findings

  • LegalSource — title, authority, country_code, level, article_ref, url, content_hash, embedding[1536], status
  • RiskFinding — clause_ref, risk_level, confidence, matched_sources[], obsolescence_flag, conflict_flag, recommendation
  • ReportVersion — version, global_score, confidence_global, severity_counts{}, report1/2_markdown, parent_version_id

Admin & Gouvernance

  • ScoringRule — domain, country_code, weights{}, confidence_thresholds
  • LLMConfig — provider, model, temperature, system_prompt, version
  • CountryModule — country_code, is_active, legal_sources_count
  • AuditLog — user_id, action, entity_type/id, diff{}, timestamp

🚀 Démarrage & Commandes Utiles

Installation

# 1. Cloner & configurer
git clone 
cd ece
cp .env.example .env
# Éditer .env : OPENAI_API_KEY=sk-... ou ANTHROPIC_API_KEY=sk-ant-...

# 2. Lancer (premier build ~3-5 min)
docker-compose up --build

# 3. Accéder
# Frontend: http://localhost:3000
# API Swagger: http://localhost:8000/docs
# MinIO Console: http://localhost:9001 (minioadmin/minioadmin)
# Admin par défaut: admin@ece.local / admin123

Développement Backend

# Logs workers
docker-compose logs -f celery-worker

# Shell backend
docker-compose exec backend bash
# ou
docker-compose exec backend python -m pytest

# Réinitialiser DB
docker-compose down -v && docker-compose up --build

Développement Frontend

# Shell frontend
docker-compose exec frontend bash
# ou
cd frontend && npm run dev

# Lint / Type check
npm run lint
npx tsc --noEmit

📚 Apprentissages Clés à Réutiliser

1. Plan-first avec flipped interaction — Scope → PRD → Spec → Build. Chaque phase valide les décisions avant le code. Les docs dans devpost/ portent le contexte entre sessions.
2. Build par tranches (slices) end-to-end — Pas de couche horizontale isolée. Slice 1 = stack complet + auth + projet. Slice 3 = noyau RAG. Chaque slice laisse l'app fonctionnelle et committée.
3. Mode mixte Learn/Fast — Learn pour le noyau métier (RAG, scoring, incrémental) où l'apprenant valide chaque choix de design. Fast pour le boilerplate (auth, CRUD, UI).
4. Mock LLM pour développement — Développement offline, tests déterministes, CI sans coûts. Le vrai LLM s'active via variable d'env.
5. Corpus versionné + recherche hybride — PGVector pour similarité + SQL pour filtres exacts. Métadonnées riches (hash, URL, autorité, dates) pour traçabilité et détection d'obsolescence.
6. Mise à jour incrémentale par diff — Identifier les findings impactés → re-run ciblé → nouvelle version avec parent_id → diff algorithmique pour l'UI. Évite la ré-analyse complète.
